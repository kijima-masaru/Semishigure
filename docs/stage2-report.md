## 完了条件の確認

「N を実行中に 5→20→8 と変えて追従する」

```
semishigure load examples/dev-freeswitch.yaml --schedule "5:40,20:40,8:40" --duration 60 --ramp 1
```

ステップスケジュールで目標同時数を 5（40 秒）→ 20（40 秒）→ 8（40 秒）→ 0 と変え、コントローラが追従した。
発信 28 本、確立 28 本、失敗 0 本。通話長 60 秒を超えた通話は自動で BYE され、コントローラが補充した（`duration_elapsed` 8 本、`drain` 20 本、終了時 `stop` None 本）。

## 段階 2 で入れたもの

- 負荷コントローラ（`semishigure/core/controller.py`）: 100 ms 周期、目標 N への追従、ramp_rate のトークンバケット、drain_rate で古い順に切断、call_duration の自動 BYE、一時停止、バースト、ステップスケジュール、プリセット A/B、486/503 連続時の自動減少、絶対上限 50 と prod の確認・上限 20
- 統計（`core/stats.py`）: 発信/確立/失敗/終了理由、INVITE→200 の p50/p95、RTP 遅れ、応答内線の分布、1 秒時系列
- ラン保存（`core/store.py`）: SQLite に runs / samples / calls / events
- API + WebSocket + UI（`api/app.py`、`ui/static/index.html`）: スライダー、±1/±5、バースト、一時停止、全切断、スケジュール、プリセット、統計タイル、時系列グラフ、通話一覧、過去ラン
- CLI `semishigure load`（ヘッドレス実行）と `semishigure serve`（UI）

## 段階 2 で直した不具合

- 通話長経過や drain の切断が BYE を送らず、アプリ側だけ終了していた（PBX 側に通話が残り、着信グループの通話制限 20 に当たって 486 が連鎖した）
- 直前に終了した通話（失敗を含む）を 0.5 秒間は「占有中」と数え、PBX のチャネル解放を待ってから補充する。ただし drain の判定には使わない
- 同時鳴動のグループ化に、発信側が付ける `X-Semishigure-Call` ヘッダーを使う（FreeSWITCH が B レグにコピーする）。同じ発信者の別通話が同時に鳴っても混ざらない
